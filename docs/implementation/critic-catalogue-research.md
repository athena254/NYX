# Critic catalogue research: candidates beyond C-001..C-010

**Status:** research only. Nothing here is implemented, and no phase is gated on it.
**Date:** 24 October 2026.
**Method:** read the actual critic pack (`src/nyx/critics/c001..c010`, `base.py`, `context.py`,
`registry.py`), the SPEC §8 contract, the domain enums, the transcript adapter
(`src/nyx/adapters/agent_transcript/`), and the roadmap; then mapped established
failure-taxonomy literature onto the seams NYX actually exposes. Every NYX claim below is
verified against the code, not assumed.

**Purpose:** answer two questions — what else *can* NYX criticise, and do the critics
*collaborate* to catch things none of them catches alone.

---

## 1. What NYX can see, and therefore what it can criticise

A critic receives a `CriticContext` (`src/nyx/critics/context.py`) containing exactly:

| Field | What it is | Used by |
| --- | --- | --- |
| `target_event` | the observation that triggered the run | C-006, C-009, C-010 |
| `linked_claim` | the claim the event refers to, if any | C-001..C-005, C-007, C-008 |
| `related_claims` | other stored claims about the same artifact | C-002 |
| `linked_evidence` | evidence linked to the claim or named by the event | C-001, C-003..C-009 |
| `scope` | resolved scope (claim's, else event-derived) | all |
| `now` | clock reading taken when the context was built | freshness checks |

Verified from the code, the pack's current blind spots:

- **Only `claim_type == COMPLETION` is ever read.** `grep ClaimType.` over `src/nyx/critics/`
  returns two hits, both `COMPLETION`. `ClaimType` has eight values (`enums.py`: FACTUAL,
  CAUSAL, PREDICTIVE, POLICY, COMPLETION, SECURITY, QUALITY, OTHER). Seven are uncriticised.
- **`event_type` is read by no critic.** `Event.event_type` (`domain/events.py`) is carried
  into every context and never inspected. The Git/CI adapter emits typed events and the
  transcript adapter emits `agent.turn`; nothing checks whether the *kind* of event is
  coherent with the *content* it claims.
- **Every critic is a single rule.** SPEC §8 fixes ten critics, each one narrow. Nothing
  composes them, and `run_selected` (`registry.py`) executes them independently against one
  context. There is no meta-critic that reads other critics' results.
- **Evidence's own metadata is barely read.** `integrity_method`, `verification`,
  `sensitivity`, `access_policy_ref`, `retention_class`, `content_hash`, and
  `producer_identity` are all on `EvidenceItem` (`domain/evidence.py`) and none is examined
  by any critic except `producer_identity` as an approval proxy (C-005).
- **`related_claims` is fetch-limited to 200 and same-artifact only** (`registry.py`
  `_related_claims`). Cross-artifact contradiction is structurally out of reach.

Those four facts are the whole opportunity. Every candidate below attaches to one of them.

## 2. The literature, reduced to critic-shaped rules

Each source was read for *failure modes*, not for padding. The rule each one licenses is
stated after it.

### 2.1 Test and CI evidence

- **Flaky tests.** A flaky test is one that passes and fails on the *same code*
  (Luo et al. 2014; Parry et al. 2021 — both cited in the literature). Detection requires
  observing both verdicts at the same commit. NYX already groups runs by
  (system, artifact, kind, title) in C-009 and C-007, so the same grouping identifies
  flakiness: same defined test, same declared commit *and* environment, one pass and one
  fail.
- **Pass@k inflation.** `pass@k` reports whether *any* of k attempts passed, so k>1 inflates
  a score; benchmark contamination and leakage are documented failure modes of reported
  scores. A critic can flag when a claim's support is a *count* of attempts rather than a
  *verified outcome* — the claim says "passes", the evidence records "1 of 10 attempts".
- **Confidence-as-evidence.** Reward-hacking surveys document LLM-judge position, verbosity,
  and self-enhancement biases as *systematic*, not incidental. NYX's own C-008 already says
  certainty must be proportionate to evidence; the literature says the proportion test must
  also cover *where the certainty came from* (a model's self-assessment is a weaker basis
  than a recorded run).

### 2.2 Supply chain and provenance

- **SLSA build levels.** L1 = provenance exists; L2 = provenance is authentic (signed);
  L3 = non-forgeable (generated by a trusted control plane). `EvidenceItem.integrity_method`
  already carries NONE / HASH / SIGNED / ATTESTED / EXTERNAL — NYX has the field and no
  critic reads it.
- **W3C VC Data Integrity.** A proof names a `type`, parameters, and a `verificationMethod`;
  verification is a *distinct* step from evaluating the truth of the claims inside. This is
  exactly NYX's own split (SPEC ADR 0005, "evidence is not proof"), which means a critic can
  demand the two be stated separately rather than conflated.
- **Data classification policy.** Classification is a label plus *handling rules*; a correct
  label still fails when the handling rule is absent (ISO 27001 A.5.12). `EvidenceItem`
  carries `sensitivity` *and* `access_policy_ref` — the label and the rule, side by side.

### 2.3 Claim quality and verifiability

- **INCOSE / NASA requirements guidance.** A statement that cannot be tested, inspected,
  analysed, or demonstrated is not a requirement — vague terms ("fast", "adequate",
  "user-friendly", "maximize") make it unverifiable. `Claim.statement` is free text up to
  2000 chars and nothing checks whether it is *checkable*.
- **Benchmark validity.** "What was actually tested, and does the claim match?" is the
  three-step validity framework; a construct claim ("intelligent", "reliable") cannot be
  supported by a criterion measurement (an accuracy number) without an explicit argument.
  NYX's C-008 handles *wording* vs *evidence count*; it does not handle *construct* vs
  *criterion*.
- **Self-reported verification.** An agent's own prose claim that a check passed is
  unfalsifiable inside the conversation; the check must be a tool result or a recorded run.
  This is the documented reason a verification ledger is append-only and SELECT-only. NYX
  now *ingests agent transcripts* — this gap is live, not theoretical.
- **Internal vs external consistency.** Internal consistency (do the parts agree) is a
  *necessary but not sufficient* condition for validity. NYX's C-010 is internal
  consistency of its own store. Nothing performs external consistency: does the claim agree
  with the world it describes?
- **Retraction grounds (COPE).** "Findings are unreliable" — major error, fabrication,
  falsification, redundant publication, unauthorised material, compromised peer review.
  Several of these are *structural* facts about a record (duplicate publication =
  near-identical claims presented as independent) rather than judgements of truth.

### 2.4 Agent and trajectory evaluation

- **Trajectory rubrics** (AgentBoard/T-Eval lineage) score goal progress, evidence grounding,
  execution/tool handling, and recovery — *separately from task success*, because "a correct
  answer may hide unsafe tool use, policy violations, unnecessary retries, or poorly
  grounded intermediate reasoning". NYX has the transcript adapter that could feed these;
  no critic consumes a trajectory.
- **Agent failure taxonomies.** MAST (NeurIPS 2025) catalogues 14 failure modes across
  specification, inter-agent misalignment, and task verification from 1,642 traces.
  DevAgentBench's nine categories add problem-understanding, planning/decomposition,
  context/memory, tool usage, partial-change/regression, and safety/security. Aegis adds
  state-awareness and tool-output-processing failures. Two of these — **step loops** (the
  same action repeated without progress) and **premature termination** (stopping before the
  task is done) — are structurally detectable from a transcript's tool-call sequence.
- **Reward hacking in agentic systems** escalates from feature-level (verbosity, sycophancy)
  through evaluator-level (LLM-judge gaming) to environment-level (test modification, log
  suppression, monitor disruption). The environment-level ones are the ones a critic service
  is positioned to notice: the *observation channel* is the thing being manipulated.

### 2.5 Evidence-synthesis methodology

- **PRISMA** distinguishes publication bias (studies missing) from selective reporting bias
  (outcomes within a study reported selectively), and treats **duplicate publication** as a
  distinct, checkable condition — the same study reported more than once, which inflates
  the evidence base. The Cochrane guidance is explicit that semi-duplicate publications
  should be *combined into one finding* rather than counted separately.
- **De-duplication literature** is blunt about the trade: automated matching produces both
  false negatives (near-duplicates missed) and false positives (distinct records merged).
  The accepted shape is *detect candidates, resolve by hand* — which is precisely NYX's
  `finding` + human disposition model.
- **Reproducibility vs replicability.** Reproducibility = same data, same method, same
  result. Replicability = same question, new data. NYX's C-007 already surfaces
  "the same test, later failing" as a regression; it does not ask whether the two runs were
  *independent* or the same run reported twice.

### 2.6 Uncertainty communication

- **Uncertainty statements.** "We can't prove X conclusively" and "we have no evidence of X"
  both *look* like uncertainty while signalling opposite leanings; a faithful uncertainty
  statement names the method, the inputs, and the residual doubt. Applied to NYX: a claim
  that is uncertain *should say so*, and a claim that hides its uncertainty is criticisable
  on the same grounds as one that overstates it.

## 3. Candidate critics

Grouped by the blind spot each one closes. Each entry states the rule, the trigger, the
evidence it reads, and what it must *not* claim.

### Tier 1 — high value, fits the existing contract cleanly

**C-011 — Claim verifiability (unfalsifiable statement)**
- *Rule:* a claim whose statement contains no measurable criterion, no named method, and no
  scope-narrowing detail cannot be assessed by anything — so NYX should say so rather than
  treat it as a normal claim.
- *Trigger:* hedging/unmeasurable markers in `Claim.statement` ("adequate", "fast",
  "sufficient", "user-friendly", "maximize", "minimize", "as appropriate", "when required"),
  combined with no linked verification evidence and no named scope field beyond `system_id`.
- *Reads:* `linked_claim.statement`, `linked_claim.scope`, `linked_evidence`.
- *Category:* `UNSUPPORTED_CLAIM` (or `OTHER`). *Severity:* LOW–MEDIUM.
- *Must not claim:* that the claim is false. Only that it is not checkable as written.
- *Source basis:* INCOSE R7 / NASA unverifiable-term lists; SPJOR "verifiable" criterion.

**C-012 — Claim type coverage (seven of eight claim types uncriticised)**
- *Rule:* every `ClaimType` should have at least one check. FACTUAL claims need a source
  that states them; PREDICTIVE claims need a stated method and an evaluation window; CAUSAL
  claims need the mechanism named; POLICY claims need the policy version they invoke;
  SECURITY claims need the threat model or scan behind them; QUALITY claims need the
  measured metric.
- *Trigger:* `linked_claim.claim_type` is set and no linked evidence matches the type's
  required support.
- *Reads:* `linked_claim.claim_type`, `linked_evidence.kind`.
- *Category:* `MISSING_VERIFICATION`. *Severity:* MEDIUM.
- *Must not claim:* the claim is untrue — only that its type's expected support is absent.
- *Why this one:* it is the single largest measured gap in the pack (verified by grep) and it
  is a *coverage* critic, so it degrades gracefully as types are added.

**C-013 — Event/content coherence**
- *Rule:* the declared event type should be consistent with the evidence linked to it.
- *Trigger:* `agent.turn` event whose only linked evidence is itself a transcript tool call
  (circular); or a `ci_test_result` event carrying no verification evidence; or an event
  declaring a completion whose linked evidence is a `REVIEW_RECORD` only.
- *Reads:* `target_event.event_type`, `linked_evidence.kind`, `target_event.labels`.
- *Category:* `OTHER`. *Severity:* LOW.
- *Must not claim:* the event is fraudulent — only that its declared type and its evidence
  do not line up.

**C-014 — Evidence integrity and sensitivity handling**
- *Rule:* evidence should carry the integrity method and handling rule its sensitivity
  implies.
- *Trigger:* `sensitivity` in {CONFIDENTIAL, RESTRICTED} with `integrity_method` NONE, or a
  `source_ref` that is a bare string with no `locator`, or `access_policy_ref` present but
  `sensitivity` PUBLIC on evidence that carries restricted-shaped content.
- *Reads:* `EvidenceItem.integrity_method`, `sensitivity`, `access_policy_ref`, `locator`.
- *Category:* `OTHER` (or `SECURITY_RISK` for the integrity half). *Severity:* MEDIUM–HIGH.
- *Must not claim:* the evidence is authentic or inauthentic — only that the declared
  handling does not match the declared sensitivity. (ADR 0005: evidence is not proof.)
- *Source basis:* SLSA levels; W3C VC Data Integrity; ISO 27001 A.5.12 classification.

**C-015 — Duplicate and semi-duplicate evidence**
- *Rule:* two evidence items that are the same artifact reported twice inflate the evidence
  base and must be surfaced as candidates, not merged.
- *Trigger:* equal `content_hash`, or near-identical `(title, source_ref, captured_at)` with
  different ids; or two claims with the same normalized statement about the same scope.
- *Reads:* `linked_evidence` (hash, title, source_ref, captured_at); `related_claims`.
- *Category:* `OTHER`. *Severity:* LOW. *Result:* FINDING with `requires_human_review=True`.
- *Must not claim:* which is the duplicate. Detection only; resolution is human.
- *Source basis:* PRISMA item 15–16, Cochrane duplicate-publication guidance, de-dup
  literature (detect candidates, resolve by hand).

### Tier 2 — needs one new field or one new read path

**C-016 — Flaky test detection**
- *Rule:* the same defined test recording both a pass and a fail at the *same* declared
  commit and environment is flaky, not a regression.
- *Trigger:* C-009's grouping plus an equality test on commit *and* environment. This is the
  one case where C-009's "definitely comparable" pair is *not* a conflict — it is noise.
- *Reads:* same as C-009, plus `scope.commit` and `scope.environment` equality.
- *Category:* `QUALITY_RISK`. *Severity:* MEDIUM. *Result:* FINDING (or INCONCLUSIVE).
- *Must not claim:* which run is right. Flakiness *is* the finding.
- *Source basis:* Luo et al. 2014 / Parry et al. 2021 definitions.

**C-017 — Selective reporting (one-sided evidence)**
- *Rule:* if a claim is supported by evidence that all records the *same* outcome, and a
  sibling claim or run records the opposite outcome at a comparable scope, the evidence base
  is one-sided.
- *Trigger:* a claim's linked evidence is unanimous while `related_claims` (or the wider
  store, if the read path is widened) holds a disagreeing outcome for the same scope.
- *Reads:* `linked_evidence`, `related_claims`.
- *Category:* `UNSUPPORTED_CLAIM`. *Severity:* MEDIUM.
- *Must not claim:* that the suppressed outcome is true — only that the presented base is
  one-sided.
- *Source basis:* PRISMA selective reporting bias / publication bias.

**C-018 — Trajectory-level critic (step loops, premature termination, unrecovered failures)**
- *Rule:* a trajectory that repeats the same tool call with the same arguments without an
  intervening observation, or that ends while a declared subtask has no evidence, or that
  records a tool error with no later retry, is criticisable independently of whether the
  final answer was right.
- *Trigger:* transcript-derived events (`agent.turn`) with repeated `(tool, arguments)`
  tuples, or a session whose last event has no terminal evidence.
- *Reads:* a new read path over events for one `correlation_id` (the transcript adapter
  already sets `correlation_id = system_id:turn_id`).
- *Category:* `QUALITY_RISK`. *Severity:* MEDIUM.
- *Must not claim:* the task failed — only that the *process* shows a documented failure
  pattern. (Aegis, MAST, DevAgentBench all separate process from outcome.)
- *Cost:* needs the store read, so it belongs with C-010 in `register_storage_backed`.

**C-019 — External consistency (claim vs. world)**
- *Rule:* internal consistency (C-010) is necessary but not sufficient; a claim should be
  checkable against an independent source, and NYX should say when none is linked.
- *Trigger:* a claim with only self-produced evidence — every linked item's
  `producer_identity.id` equals `claim.claimant_system_id`.
- *Reads:* `linked_evidence.producer_identity`, `linked_claim.claimant_system_id`.
- *Category:* `UNSUPPORTED_CLAIM`. *Severity:* LOW–MEDIUM.
- *Must not claim:* the claim is false — only that it rests entirely on the claimant's own
  output.
- *Source basis:* internal/external consistency distinction; self-reported verification
  literature.

**C-020 — Uncertainty disclosure**
- *Rule:* a claim that asserts certainty while its own linked evidence carries explicit
  limitations, or that omits an uncertainty statement when the evidence is thin, is
  criticisable on proportionality grounds.
- *Trigger:* C-008's universal markers **or** `EvidenceItem.limitations` non-empty while the
  claim asserts a definitive outcome.
- *Reads:* `linked_claim.statement`, `linked_evidence.limitations`.
- *Category:* `UNSUPPORTED_CLAIM`. *Severity:* LOW.
- *Must not claim:* the claim is wrong — only that its certainty is not proportionate to
  the limitations the evidence itself records.

### Tier 3 — optional, speculative, or needs a phase

**C-021 — Benchmark validity (construct vs. criterion).** Flags claims that assert a
construct ("reliable", "safe", "intelligent") supported only by a criterion measurement
(an accuracy or pass rate). Needs a mapping from claim wording to construct class; that is a
judgement, so it belongs with the Phase 6 model critics rather than the deterministic pack.

**C-022 — Reward-channel manipulation.** Detects when an agent's *observation channel* is the
thing being altered (a test file edited, a log suppressed, a monitor disabled). This is the
environment-level reward-hacking tier. It requires reading the transcript's tool arguments
for writes to test/config paths — doable from the adapter's `ToolCall.arguments`, but it is
an inference, not a structural fact, and it should be marked as an assessment.

**C-023 — Construct-claim / criterion-claim mismatch** (a cleaner restatement of C-021, kept
separate because it can be made deterministic: the claim asserts a property, the evidence is
a measurement, and no stated rule connects them).

**C-024 — Claim/evidence duplication across systems.** Same as C-015 but across
`claimant_system_id` — needs `_related_claims` widened beyond same-artifact, which is a
`registry.py` change.

## 4. Do the critics collaborate?

**Not today, and this is the most important finding.** `run_selected` (`registry.py`) builds
one context, then runs each critic independently and persists each result. There is no
composition, no shared state, and no critic that reads another's output. C-010 is the only
meta-level check, and it audits *NYX's own store*, not the other critics' conclusions.

Three concrete consequences, each verified in the code:

1. **A single critic's scope boundary is a silent gap.** C-008 returns `no_finding` when a
   claim has *no* linked evidence, on the stated grounds that "missing verification is the
   completion critic's finding". But C-001 returns `no_finding` when the claim is not a
   COMPLETION claim. A universal claim with no evidence and a non-completion type is
   therefore reported by *neither*. That is a real blind spot, not a theoretical one.
2. **C-009 abstains where C-007 concludes.** C-009 returns `INCONCLUSIVE` on a pass/fail pair
   at a comparable scope. C-007 returns FINDING on a pass-then-fail sequence. Both can fire
   on the same evidence with different verdicts, and nothing reconciles them. Flakiness
   (C-016) is the resolution: same commit *and* environment → flaky, not a regression.
3. **Two critics fire on the same underlying defect with different severity.** C-001
   (missing verification) and C-012 (claim type coverage) would both flag a bare factual
   claim. Without composition, that is two findings for one defect — which is exactly the
   duplicate-publication problem NYX's own methodology warns about.

### What collaboration would look like

Ordered from cheapest to most invasive:

**A. Composition rules over existing results (no new infrastructure).** A post-run pass over
the `CriticRunOutcome` list, persisted as a *derived* note rather than a new finding, that:
- suppresses a C-008 result when C-001 has already raised the missing-verification finding
  (one defect, one finding);
- re-labels a C-007 regression as *flaky* when the same test shows a pass and fail at an
  equal commit and environment;
- marks C-015/C-017 duplicate and one-sided-evidence findings as human-review candidates
  rather than letting them sit as independent verdicts.

This is the highest-value change and it touches nothing in the critic contract.

**B. A declared collaboration table.** SPEC §8 is a flat list. A short table naming which
critic *owns* each defect class — and which abstains when another owns it — would make the
silent-gap problem in consequence 1 impossible to reintroduce, and would give the acceptance
scenarios something to test. The C-008/C-001 gap is the proof it is needed.

**C. A cross-critic meta-critic.** A critic that receives the *other critics' results* as
its context and reports only *interactions*: two critics disagreeing, two critics firing on
one defect, a critic whose `no_finding` is contradicted by another's FINDING. This is the
"niche criticism" the question asks about — it is the only shape that catches a class of
defect no single rule can see. It needs a context extension (`CriticContext` currently has no
field for peer results) and it must be deterministic, so it is a Phase 2-class change, not a
tweak.

**D. Pairing with the Phase 6 model critics.** The deterministic pack is strong on *structure*
and weak on *meaning*. The right collaboration is not deterministic-plus-deterministic but
deterministic-plus-model: the deterministic critic says "these two runs disagree at the same
commit", and the model critic is asked only "is this flakiness or a real regression, and what
would distinguish them" — with its answer recorded as an *assessment*, never as a verdict
(SPEC Phase 6 non-goal). That is the division of labour NYX's own rules imply.

## 5. Recommended order

1. **C-012** (claim type coverage) — largest measured gap, pure extension of existing reads,
   no new field, no new read path.
2. **C-011** (verifiability) — same shape, closes the "unfalsifiable claim" class.
3. **C-015** (duplicate evidence) — cheap, and it is the prerequisite for trusting any
   multi-evidence conclusion.
4. **Composition rules (A)** — fixes consequences 1 and 2 without new critics.
5. **C-014** (integrity/sensitivity) — needs `EvidenceItem` fields that already exist.
6. **C-016** (flakiness) — resolves the C-007/C-009 overlap.
7. **C-018** (trajectory) — needs the store read path; bundle with C-010.
8. **C-021/C-022** — Phase 6, model-assisted, marked as assessment.

## 6. What this research does not establish

- No candidate has been implemented or tested. Every rule above is a design, not a verified
  behaviour.
- The literature is used for *failure modes*, not for thresholds. Any numeric threshold
  (how similar is a duplicate, how many attempts before pass@k is suspect) needs its own
  calibration and belongs with the Phase 6 evaluation corpus.
- Nothing here changes SPEC §8. The ten critics are the contract; these are additions, and
  adding one is a SPEC change plus an ADR, not a code change alone.
